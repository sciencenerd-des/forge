Purpose

Evolve Forge from a resilient harness (it survives failures) into a convergent one (it measurably approaches the goal and can prove it). This plan adds a quantitative progress signal, an adversarially-hardened contract layer, a hermetic verifier hierarchy, compounding failure-lesson memory, search over executor actions, and a self-improvement loop gated by its own eval suite — each phase independently shippable and pinned by regression tests, in the existing docs/LESSONS.md tradition.

Problem

Today the loop's only notions of progress are binary (contract passes / doesn't) and negative (stagnation counters, consecutive-failure budgets). Consequences:

  • No convergence signal. A run that is 90% done and one that is thrashing look identical until termination. Stagnation handling is reactive re-decomposition, not informed steering.
  • Contracts can still be gamed or weakened. Lesson 1 (false completion via a silently dropped test) was patched narrowly; nothing measures a contract's strength or detects a trivially-satisfiable one proactively.
  • One verifier, one environment. The evaluator runs tests in the same workspace the executor mutated — passing there doesn't prove the artifact is hermetic or reproducible.
  • Failures don't compound into knowledge. forge_runtime/steering.py defines a Lesson dataclass, but nothing extracts lessons from failures or retrieves them into the steward's context packs — the same small-model mistakes recur across runs.
  • The harness can't measure itself. evals/ has one incident eval; there is no benchmark suite, so any change to prompts, gates, or policies is merged on vibes.

Solution

Six layered capabilities, ordered so each one's verification machinery is available to validate the next:

PhaseCapabilityFrontier idea it operationalizes
1Convergence Ledger — per-cycle distance-to-done metric + controllerProcess-reward-style dense signal over a verifier, not model self-report
2Contract Immune System — mutation-tested, strength-scored contractsAdversarial hardening of the reward channel (anti-reward-hacking)
3Verifier Hierarchy — hermetic Docker replay + evidence recordsIndependent, reproducible verification (debate/replication over trust)
4Compounding Memory — automatic lesson extraction & retrievalExperience distillation across runs (Voyager/Reflexion-style, but grounded in verdicts)
5Action Search — best-of-N executor candidates scored by cheap verifiersInference-time search with verifier-guided selection
6Verifiable Self-Improvement — eval-gated changes to the harness itselfDarwin-Gödel-machine-lite: self-modification merged only when benchmarks improve

[x] Phase 1: Convergence Ledger & Controller

Turn the evaluator's binary verdict into a dense, persisted progress signal, and replace reactive stagnation handling with an informed controller. Distance-to-done D(t) = 1 − (weighted tests passing / total contract tests), augmented with per-test first-pass cycle and flake counts. The controller observes ΔD over a sliding window and chooses among mapped strategies: retry, re-decompose, escalate-context (bigger context pack), switch-provider-profile, or block — as an epsilon-greedy bandit whose reward is subsequent ΔD.

[x] Phase 3: Verifier Hierarchy & Hermetic Replay

"Done" graduates through tiers: T0 executor heartbeat (advisory only, as today) → T1 evaluator in-workspace run (today's ground truth) → T2 hermetic replay: the workspace is snapshotted (git archive or tar), replayed in a fresh Docker container (network off, pinned image per stack), and the contract re-run from scratch — including build steps. A goal is verified only at T2. Every verdict writes an evidence record: command, exit code, stdout/stderr digests, environment fingerprint, wall time — queryable from the console, so completion claims are auditable artifacts, not log lines.

[x] Phase 4: Compounding Memory (Lessons that actually steer)

Close the loop that steering.py's Lesson dataclass anticipates. When the controller observes a failure pattern (repeated test failure, tool error class, contract drift), a small-model extraction pass distills it into a Lesson: fingerprint (hash of failure class + test id + error signature), observation, prevention. Lessons persist per-project, dedupe on fingerprint (bump confidence instead of duplicating), and the steward retrieves the top-k lessons whose fingerprints match the active task's context into every context pack. The payoff is cross-run: run N+1 doesn't repeat run N's dead ends.

[x] Phase 5: Action Search (best-of-N with cheap verifiers)

Small models fail less when they get more shots with a referee. For high-stakes actions only (a task's attempts ≥ 2, or the controller requests it), the executor samples N=3 candidate actions at varied temperature, and a cheap verifier cascade scores each before any workspace mutation: syntax check (python -m py_compile / node --check / cargo check-dry equivalents), path-policy check (reuses tool sandbox rules), and a relevance heuristic (does the diff touch files named in the task's acceptance criteria?). The best candidate executes; the rest are logged as counterfactuals in the ledger. This is verifier-guided inference-time search — the compute goes where the run is stuck.

1. Candidate generation and scoring

  • [x] Create forge_runtime/action_search.py: generate_candidates(context, n) -> list[Action] and score(action, workspace) -> float implementing the cascade; a candidate failing syntax scores 0 and never executes
  • [x] Integrate into executor_node.py behind an activation predicate (attempts ≥ 2 or controller strategy escalate-search — add this as a sixth mapped controller arm); default path (attempt 0–1) stays single-shot to keep cost flat
  • [x] Record all candidates + scores + chosen index in the ledger for later analysis and for Phase 6's evals

2. Budget and safety

  • [x] Enforce a per-task search budget (max 3 search rounds) and a per-run token budget read from forge_config.py; exhaustion falls back to single-shot, never blocks
  • [x] Scoring runs against a copy-on-write overlay of the workspace (tmp dir), never the live workspace — mutation only after selection

[x] Phase 6: Verifiable Self-Improvement (eval-gated harness evolution)

Give the harness a measuring stick for itself, then let changes to prompts/policies/thresholds be merged only when the stick says they help. Build evals/suite/: 8–12 small deterministic goals (each completable in <15 min on a local model) with known-good contracts and expected outcomes. evals/runner.py runs the full harness against the suite and reports: verified-completion rate, mean cycles-to-done, mean D-AUC (area under the distance curve — lower is better convergence), false-completion count (must be 0), token cost. Notes

Design stance: every "autonomy" feature here is really a verification feature. Autonomy that converges is autonomy whose reward channel can't lie: dense signal (P1), un-gameable contracts (P2), independent replication (P3), remembered failure (P4), refereed search (P5), and self-change only under measurement (P6). This is the same philosophy as docs/LESSONS.md, extended from "survive failure" to "prove progress".

Research grounding

  • P1 — dense verifier-derived reward echoes process-reward-model findings: intermediate signal beats terminal-only signal for long-horizon tasks; here the "PRM" is deterministic test execution, so it cannot hallucinate.
  • P2 — mutation-testing a contract is the classic "test your tests" idea (mutation testing, PIT/mutmut) turned against reward hacking; the null-artifact probe is a cheap sound lower bound on strength.
  • P3 — hermetic replay is the reproducible-builds discipline applied to agent verdicts; T1/T2 divergence is expected to be the richest new failure-mode telemetry.
  • P4 — Reflexion/Voyager-style episodic memory, but lessons are admitted only when tied to verifier evidence, avoiding the known failure of self-generated "insights" polluting context.
  • P5 — best-of-N with a verifier cascade is inference-time scaling targeted at stuck states only, keeping the cost profile compatible with local models.
  • P6 — Darwin-Gödel-machine-shaped, with two hard safety inversions: config-whitelist (no self-modifying code) and human-in-the-loop merge.

Dependencies & ops

  • No new Python dependencies required for P1/P2/P4/P5 (stdlib + existing SQLAlchemy). P3 needs Docker at runtime only (graceful skip otherwise). If a stats helper is wanted for the bandit, uv add numpy — but plain-python is sufficient and preferred.
  • Migration 002 is additive-only; no existing table is altered, so rollback is a table drop.
  • Ledger writes are per-test per-cycle: at small-model cycle rates this is trivial volume; add a retention sweep later if needed.

Rejected alternatives

  • LLM-as-judge as a verification tier — rejected as a gate (reintroduces a fallible reward channel); acceptable later as advisory annotation only.
  • Full MCTS over task trees — cost-prohibitive for local models; the bandit-over-strategies + best-of-N pair captures most of the value at a fraction of the tokens.
  • Letting the proposer edit engine code — rejected; self-modifying code without a formal safety argument contradicts the repo's reliability-first ethos.

Sequencing rationale

P1 first because every later phase consumes the ledger (P2 logs strength events to it, P5 logs counterfactuals, P6's D-AUC metric is computed from it). P2 before P3 so hermetic replay never re-verifies a weak contract. P6 last because its benchmark exercises everything beneath it — the eval suite is, deliberately, the plan's own acceptance contract.

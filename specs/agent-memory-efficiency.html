Purpose

Make the Forge agent loop (planner → auditor → executor → evaluator) and its memory subsystem measurably more efficient: fewer redundant DB round-trips and model loads per cycle, task-aware memory retrieval instead of blind recency dumps, durable (instead of process-local) lessons, and a rationalized compression pipeline that only pays for compression when the pack is actually large.

Problem

Research of the current codebase surfaced six concrete inefficiencies:

#FindingWhereCost
1Task-blind retrieval. build_context_pack selects the top-20 memory items by importance DESC, created_at DESC only. The pgvector embedding column and search_memory() (vector + rerank) exist but are never used on the hot path, so the executor gets recent-but-irrelevant memories.app/services/__init__.py:525Wasted context tokens; weaker small-model performance
2Reranker reloaded per call. _rerank_results constructs CrossEncoder('BAAI/bge-reranker-base') inside every invocation — a multi-second model load per memory search.app/services/__init__.py:691Seconds of latency per search; repeated RAM spikes
3Hardcoded embedding backend. _generate_embedding posts to http://127.0.0.1:1234 with a fixed model — the exact failure mode already fixed once for the steward (see comment in steward.py). When it's down, embeddings stay NULL forever (no backfill).app/services/__init__.py:108Silent degradation to no-vector search
4Lessons are not durable. LessonStore is an in-process dict ("a real deployment backs this with the lessons table" — it doesn't). Every run relearns the same failures; AgentState.selected_lesson_ids points at nothing persistent.forge_runtime/lessons.py:79Compounding memory doesn't compound
5Compression runs unconditionally. compress_context_pack invokes Headroom (per-field LLM calls + a DB snapshot write) on every executor turn regardless of pack size; the size gate only exists in the local fallback. Meanwhile the steward's _BRIEF_CACHE is an unbounded module-level dict.app/context_compression.py:29, engine/src/steward.py:90Per-turn LLM + DB cost even for tiny packs; slow leak
6Duplicate state snapshots per cycle. The steward's _db_snapshot and build_context_pack query overlapping goal/task/file/test state independently each cycle, and consolidate_old_logs (memory hygiene) exists but is never scheduled by run_pge.py.engine/src/steward.py:44, run_pge.pyRedundant queries; unbounded event/memory growth

Solution

Five focused phases, each independently shippable and pinned by tests. (1) Make retrieval task-aware: score memories against the active task via vector search when available, tsvector otherwise, blended with importance/confidence — and cache the reranker at module level. (2) Route embeddings through forge_config provider profiles with a lazy backfill so NULL embeddings heal. (3) Back LessonStore with hermes_memory_items (type lesson, fingerprint in tags) so lessons survive restarts and flow into the pack. (4) Gate Headroom behind the same size threshold as the fallback, bound the steward cache, and log pack token counts to hermes_context_pack_logs for observability. (5) Share one DB snapshot per cycle between steward and pack builder, and schedule consolidate_old_logs + lesson decay at batch boundaries in run_pge.py.

Notes

Design constraint carried from docs/LESSONS.md: every memory/compression path must be best-effort — a failure degrades to a deterministic fallback and never blocks or crashes the loop. Every task above preserves that contract; the new tests assert it explicitly.

What is deliberately out of scope: replacing the four-node PGE loop, changing the Postgres schema (everything fits existing columns — tags, confidence, status, and the already-provisioned pgvector column and hermes_context_pack_logs table), and touching forge_runtime/context_compactor.py's transcript folding, which is already deterministic and cheap.

Rejected alternatives: (a) a dedicated lessons table — the migration comment references one, but hermes_memory_items already has every needed column and the pack filter for free; a new table adds a migration and a second retrieval path for no capability. (b) Always-on cross-encoder reranking — quality win is real but the 400MB model load contradicts the small/local-first design; hence opt-in. (c) Replacing Headroom with the local compactor entirely — Headroom's reversible snapshots have audit value; gating fixes the cost without losing it.

Dependencies: none new for Phases 1–5. sentence-transformers and headroom remain optional imports guarded exactly as today. Phase 6 adds only opt-in Docker/SQL artifacts — the Python side degrades to plain-table/app-side fallbacks when extensions are absent.

Research grounding (Phase 6)

The durable-substrate experiments are deliberately mapped to prior art rather than invented; each experiment cites the pattern it operationalizes:

Honesty notes on the candidate list: pg_boss is a Node.js library (not a Postgres extension) and pg_timetable is an external Go scheduler binary — both are recorded as alternatives in the triage doc, not installed. pg_durable, pg_later, pg_task, and pg_net are young or niche enough that the plan requires verifying packaging/pg16 support before any code depends on them; pg_net's async-HTTP-from-SQL is explicitly deferred — LLM calls from inside the database would blur the tool/runtime authority boundary the Agent-libOS line of work argues for keeping crisp.

Expected impact per cycle: ~2 fewer DB query bursts (shared snapshot), zero Headroom LLM calls for small packs (the common case early in a run), one-time-instead-of-per-call reranker load, and memory sections filled with task-relevant items under an explicit char budget — directly serving the ARCHITECTURE.md promise that "a small model isn't drowned in history."

Purpose

Turn Forge's recent harness work into a trustworthy measurement system. Preserve what already works well—fresh projects, durable launcher manifests, bounded execution, resource-contained sandboxes, deterministic evaluator tests, and a false-completion gate—while removing the paths that currently produce false greens, orphaned runs, unsafe verification, incomparable metrics, or misleading benchmark statistics.

Completion definition: this plan is successful when every attempted goal produces an auditable and reproducible terminal verdict. A low model success rate can be honest. A high rate derived from weak contracts, missing metrics, or stale lifecycle state is a harness failure.

Problem

The latest artifacts show real model capability, but they also prove that the current green count is not a reliable benchmark. The July 13 non-sandbox runs report three completions; independent goal-specific checks performed during this review accept only RPN, reject LRU, and cannot verify digits because the verifier runtime lacks sklearn. The sandbox rerun exposes important safety and tooling defects, then times out without terminating the detached child or closing its manifest.

Strong suits to preserve and amplify

Fresh, sequential projects

The canonical eight-goal driver creates a new project per goal and sequences work within one process, reducing state leakage and local-model contention.

Durable launcher evidence

goal_suite_tui.py uses the real detached launcher path, giving each run a run ID, manifest, log, process group, and control-plane visibility.

Fail-honest instincts

Missing backends become skips, false completion is intended to hard-fail the gate, and lifecycle disagreement is surfaced instead of silently greened.

Sandbox boundary

The default container is non-root, capability-dropped, no-new-privileges, volume-backed, and resource limited. This is the right execution boundary to strengthen.

Behavioral acceptance direction

The uncommitted evals/acceptance.py adds goal-specific, artifact-aware checks and already catches the recorded LRU false green.

Focused test coverage

The current acceptance, manifest, TUI, runtime-snapshot, command, and sandbox slice passes 65 tests with 4 Docker-gated skips; Ruff is clean on the reviewed files.

Solution

Build a versioned evidence pipeline around the existing launcher and sandbox. One orchestration service acquires an evaluation lease, performs deterministic preflight, launches a run, owns its total budget, terminates it cleanly, exports the authoritative container snapshot, executes a goal-specific contract in a second verifier container, and atomically records a schema-validated result. The gate compares only compatible evidence and refuses missing metrics. The Pi benchmark follows the same evidence rules: validated protocol, validated scenarios, raw measurements, and no claim from aborted turns.

[] Phase 3: Make Sandbox Tooling Deterministic

Preserve the strong container boundary while removing the argument, dependency, and daemon-health loops exposed by the sandbox digits run.

1. Preserve argv versus shell semantics

  • [] Normalize model output into an explicit internal CommandSpec(kind="argv"|"shell"). A list remains argv; a string is shell.
  • [] Treat only standalone operator tokens (&&, ||, |, redirects) as a malformed shell-packed list. Quote every non-operator token when converting it. A semicolon inside python3 -c "..." remains data.
  • [] Route all execution through Workspace.run; remove duplicate host/shell subprocess branches from the executor.

2. Deterministic dependencies and failure feedback

  • [] Pin numpy/scikit-learn in the sandbox/verifier image used by the canonical suite, and record its digest in every result.
  • [] Translate only simple, allowlisted pip install PACKAGE... requests into install_deps; reject unsupported flags with a precise message. Do not execute system-pip mutation.
  • [] Detect repeated identical tool failures by normalized action + error class. After two repeats, inject the deterministic recovery instruction or block honestly; do not spend the entire goal budget on PEP 668.
  • [] Classify Docker command timeout/daemon unresponsiveness as infrastructure failure, capture container resource state when possible, terminate the run, and prevent the next goal from starting until preflight is healthy.

3. Snapshot authority

  • [] Add a read-only export_snapshot() method to Workspace that stages an immutable copy without overwriting the project's host mirror.
  • [] Export only after the child is terminal; strip .git, internal probes, caches, and dependency directories; calculate a content digest.

Notes

Acceptance criteria

  • Every suite goal has a schema-valid result with run/project IDs, terminal reason, snapshot digest, acceptance evidence, and environment fingerprint.
  • A timeout leaves no live child/process group, no held lease, and no stale running manifest.
  • No agent-produced code is executed on the host by a gateable acceptance run.
  • The recorded incomplete LRU solution cannot pass; the recorded RPN solution can pass; digits yields a behavioral verdict rather than a missing-dependency error.
  • blocked run + active goal is classified as resumable, while completed run + active goal is inconsistent.
  • Argv-form python3 -c "import sklearn; print(...)" executes with the code string intact.
  • Missing cycles/D-AUC/token metrics remain null and cause a comparison failure; they never become favorable zeros.
  • Pi V2 reports p95 greater than or equal to median, completed agent_end turns, scenario validity, raw sample counts, and explicit abort exclusions.
  • The V2 baseline describes harness truth; it does not promise 8/8 model completion.

Implementation assumptions

  • The current dirty working tree is user-owned and must be preserved. Integrate with the uncommitted acceptance/TUI/sandbox changes rather than replacing them wholesale.
  • No persistent LM Studio, Ollama, provider, context-length, or model-load configuration is changed. Live qualification receives process-local arguments only.
  • The canonical suite remains sequential because the machine has one primary local-model capacity pool. The global lease extends that guarantee across processes.
  • Pydantic is already a project dependency, so the V2 result schema requires no new Python dependency.
  • Pinning sklearn/numpy in the canonical image is justified because the suite explicitly contains a sklearn goal and reproducible verification requires that runtime.

Learning note

A benchmark is a product boundary, not a reporting script. Its state machine, execution sandbox, acceptance contract, and statistics all participate in correctness. A strong harness does not maximize green results; it maximizes the amount of trustworthy information each expensive run produces.

Purpose

Close the gaps that survived the Cycle-1 implementation review of PR #6: (1) make the control-plane contract fixtures generated by the real FastAPI handlers instead of hand-typed twins, (2) complete the Pi session experience (stats footer, session picker, steer/follow-up, multi-line editor, verified spawn flags, dialog timeouts), (3) polish the operator seams that still behave inconsistently (watch-mode offline fallback, promote-to-goal project awareness, a flood test that drives the real event loop), and (4) run the evidence work the Cycle-1 plan deferred — a Pi built-in tool latency benchmark that decides the forge-tools RFC, and the small A2A client that was always post-MVP.

Problem

Cycle 1 shipped a green, well-tested MVP, but four classes of debt remain. Contract: tests/contract/test_fixture_export.py builds its samples as hand-written literal dicts and asserts the committed files equal those same dicts — the Python side can drift from runtime_snapshot.py or the Pydantic schemas and every test stays green (the RuntimeRunSnapshot response_model added in Cycle 1 covers only one of eight fixture shapes). Session: the TUI always spawns pi --no-session and ignores provider/model flags; there is no session stats footer, no session picker (switch_session/ fork are typed in PiCommand but unreachable from any UI), esc can only abort (no steer/follow-up), the editor is a single-line String, dialog timeouts are never auto-resolved, and forge session --resume passes a flag that is not in Pi 0.80.2's documented session-flag set (--session/--fork/--no-session) — it may fail at spawn. Operator: run list --watch hard-errors where the non-watch path falls back offline; promote-to-goal cannot pick a project and only learns about an already-running project after posting; the flood test exercises toy channels, not the real event loop. Evidence: the forge-tools backlog decision is blocked on a benchmark nobody has run, and the A2A client remains unimplemented.

Solution

Five bounded phases, ordered by risk. First make the contract self-verifying: serialize fixtures through FastAPI's TestClient with dependency overrides (real routing, real Pydantic response models, real auth middleware) so a handler change breaks the Python test before the Rust decoding test. Second, harden the forge-pi protocol layer: per-command timeouts, dialog timeout auto-resolve, CLI auto-cancel, and a spawn-flag matrix verified against pinned Pi 0.80.2 in the existing rust-pi-compat CI job. Third, finish session mode: get_session_stats footer, ctrl+r session picker over ~/.pi/agent/sessions, an esc menu (abort / steer / follow-up), and a tui-textarea multi-line editor. Fourth, operator polish: consistent offline fallback, project-aware promotion, and a flood test that drives the real event_loop with a TestBackend. Fifth, the evidence work: a scripted Pi tool-latency benchmark whose measured numbers become the go/no-go input for the forge-tools RFC, plus the small A2A JSON-RPC client (forge a2a send|get|cancel). Phases 1–2 are independent of 3–4 and each phase ships alone.

Design decisions

  • TestClient over raw serializer calls for fixtures: driving the HTTP layer exercises response_model coercion, auth dependency, and status codes in one pass — the closest thing to the wire the Rust client actually reads. Dependency overrides keep Postgres out of the loop; the stable fixture IDs are seeded into the stubs so diffs stay reviewable.
  • --resume resolution: Pi 0.80.2 documents --session <path>/--fork/--no-session; “resume most recent” is a picker concern, not a spawn flag. forge session --resume becomes “open the picker preselecting the newest session for this cwd”, implemented via --session. If pi --help on the pinned binary shows a native resume flag, prefer it and record that in the flag-matrix test.
  • Benchmark measures tool execution, not model latency: using tool_execution_start/end event timestamps isolates the thing forge-tools could actually improve. If the median tool round-trip is a few ms against seconds of model time, the RFC is a clean no-go and the backlog entry gets closed with data rather than opinion.
  • Editor swap risk: tui-textarea owns key handling; the wrapper must forward only editing keys and keep mode-level shortcuts (tab, ctrl+*) at the app layer, preserving every existing key-handling test unchanged.
  • Phase independence: 1–2 touch no TUI code; 3–4 touch no Python. Two PRs (1+2, 3+4+5) is the natural split if review bandwidth is tight.

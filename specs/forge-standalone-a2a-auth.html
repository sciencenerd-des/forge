Purpose

Make Forge a fully independent agentic system with no naming, schema, or code dependency on the legacy Hermes agent; consolidate all authentication and model-provider credentials into one robust backend store with a clean HTTP surface; give both the web console and the TUI a first-class "plug in your key / subscription / local model" experience; and expose Forge as an A2A (Agent2Agent protocol) agent — the Linux-Foundation-governed interop standard (v1.0, 2026) — so any A2A-capable agent or orchestrator can discover Forge via its Agent Card and delegate long-running coding tasks to it over HTTP + JSON-RPC/SSE.

Problem

Forge today carries its Hermes ancestry everywhere and its credential story is fragmented:

  • Hermes coupling. Every ORM model is Hermes* mapped to hermes_* tables (app/models/__init__.py), and ~10 modules (engine nodes, run_pge.py, forge_config.py, control_plane/runtime_snapshot.py, tools_db/*) import those names. The engine's shared LLM helpers live in engine/hermes_tools.py, which builds its own OpenAI client at import time with a hardcoded api_key="not-needed" and its own model auto-detect — completely bypassing forge_config.provider_for(), the supposed single source of truth. Docs still say "the native Hermes plugin imports this DB."
  • Fragmented, weak auth. Credentials only exist as scattered env vars (FORGE_LLM_API_KEY, per-role FORGE_<ROLE>_API_KEY). There is no persistent credential store, no way to set/test a key at runtime, and keys can leak into logs/snapshots. The control plane is guarded by a single plaintext bearer token compared with == (timing-unsafe) and shipped as a default value in .env.example.
  • No user-facing provider setup. The web console has no settings page; the Rust TUI (experimental/forge-cli) has no onboarding. Users must hand-edit .env to point at LM Studio/Ollama/vLLM or a cloud subscription.
  • No interop surface. Forge can only be driven by its own CLI/HTTP API. It publishes no Agent Card and speaks no A2A, so other agents (e.g. a Hermes-class orchestrator, LangGraph/ADK/CrewAI agents) cannot discover it or delegate tasks to it.

Solution

Four consolidations, ordered so each is independently shippable:

  1. De-Hermes the core. Rename models Hermes* → Forge* and tables hermes_* → forge_* via a rename migration (with temporary compatibility views for any external reader). Replace engine/hermes_tools.py with a provider-aware client factory in forge_runtime/llm.py that resolves everything through forge_config.provider_for(role).
  2. One credential core. New forge_runtime/credentials.py: a JSON provider-profile store at $FORGE_HOME/providers.json (chmod 600) with per-role profiles (base_url, model, api_key, auth_mode), env-var overrides preserved as highest precedence, secret masking on every read path, and a test_connection() probe. Control-plane token becomes generated-on-first-run, stored hashed, compared with secrets.compare_digest.
  3. Frontend plug-in UX. Control-plane /providers CRUD + /providers/test endpoints; a web Settings page with local-model presets (LM Studio / Ollama / vLLM) and cloud presets (OpenAI-compatible endpoints); a TUI setup screen in the Rust CLI that writes the same providers.json.
  4. A2A adapter. A new a2a/ package implementing the Agent2Agent protocol server: an Agent Card at /.well-known/agent-card.json declaring Forge's skill ("autonomous long-horizon coding"), and JSON-RPC methods message/send, message/stream (SSE), tasks/get, tasks/cancel. Incoming messages become Forge goals; the PGE loop's batches stream back as A2A task status/artifact updates through the full lifecycle (submitted → working → completed/failed/canceled). Mounted on the existing FastAPI control plane and runnable standalone via forge a2a.

[] Phase 5: A2A adapter — Forge as a pluggable agent

Implement the Agent2Agent protocol (a2a-protocol.org, Linux Foundation, v1.0): Forge publishes an Agent Card, accepts delegated tasks over HTTP + JSON-RPC, and streams progress via SSE. The adapter is a thin bridge: an incoming A2A message becomes a Forge goal; PGE batches drive the A2A task lifecycle. Forge's detached-run model (pge_launcher) is a natural fit for A2A's long-running-task semantics — the caller can disconnect and re-poll tasks/get.

1. Agent Card + discovery

  • [] a2a/agent_card.py — build the AgentCard: name "Forge", one skill (autonomous-coding: long-horizon goal execution with test-verified completion), input/output modes text/plain + application/json, capabilities.streaming = true, protocolVersion pinned to the implemented spec revision, security scheme = HTTP bearer (the control-plane token).
  • [] Serve it unauthenticated at GET /.well-known/agent-card.json on the control-plane app (discovery must not require the token; the RPC endpoint does).

2. JSON-RPC methods + task bridge

  • [] a2a/server.py — single JSON-RPC 2.0 POST endpoint (mounted at /a2a) implementing message/send, message/stream (SSE response of task status/artifact update events), tasks/get, tasks/cancel; standard JSON-RPC errors (-32600/-32601/-32602) plus A2A task-not-found.
  • [] a2a/task_bridge.py — mapping layer: A2A task ↔ Forge goal (+ contextId ↔ project). message/send resolves-or-creates a project (workspace under workspaces_root(), honoring forbidden_workspaces()), creates the goal, and launches a detached run via pge_launcher.launch_pge; task state derives from durable engine state: submitted (goal created) → working (batches running) → completed (goal verified) / failed (failure budget exhausted) / canceled. Final artifacts = file-change summary + evaluator test results.
  • [] Streaming: message/stream tails engine events (forge_events table / run manifest) and emits A2A TaskStatusUpdateEvent / TaskArtifactUpdateEvent frames; reconnect-safe because state is durable in Postgres.
  • [] Add forge a2a subcommand in forge_cli.py (serves the control-plane app; A2A routes included by default) and evaluate the official a2a-sdk Python package first — use it if stable, hand-roll the endpoint only if it isn't.

Questionables

Keep compatibility views / deprecated aliases, or hard-cut Hermes names?

Assumed: keep hermes_* SQL views and Hermes* = Forge* Python aliases for exactly one release, then drop in migrations/003. If nothing external actually reads the old names (only the retired Hermes plugin did), a hard cut is simpler — confirm before Phase 1.

Secrets at rest: plaintext-0600 JSON vs OS keychain?

Assumed: 0600 providers.json (matches SSH/aws-cli convention, works headless in Docker). OS keyring (keyring lib) is nicer on desktop but breaks containers and remote hosts. Could add keyring as an optional backend later behind FORGE_CREDENTIALS_BACKEND=keyring.

Official a2a-sdk vs hand-rolled A2A endpoint?

Assumed: try the official Python a2a-sdk first (v1.0-era, actively maintained under the Linux Foundation) and mount its ASGI app on the control plane; hand-roll the single JSON-RPC endpoint only if the SDK's server abstractions fight FastAPI or drag heavy deps. Decide at the top of Phase 5.

A2A context mapping: contextId → project, task → goal?

Assumed: one A2A contextId = one Forge project (workspace), each task = one goal. Alternative — task per PGE batch — is too granular and leaks internals. Durable Postgres state supports re-attaching streams and tasks/get after disconnects, which is A2A's main long-running-task requirement.

Should input-required be supported in v1?

Assumed no: Forge's loop is autonomous by design (blocked states end the run rather than pausing for input). If a host wants clarification round-trips, a later version can surface the planner's blocked state as A2A input-required instead of failed.

Subscription-based providers (Claude/OpenAI subscription auth) vs API keys?

Assumed: v1 supports anything OpenAI-compatible with a bearer key (covers OpenRouter, vLLM gateways, LM Studio, Ollama). OAuth/subscription flows (e.g. Claude subscription) need a device-code flow and provider-specific clients — captured as future work in Notes, not in scope.

Dependencies

  • A2A: prefer uv add a2a-sdk (official Linux Foundation Python SDK) mounted on the existing FastAPI app; fallback is a hand-rolled JSON-RPC endpoint + sse-starlette-style streaming using what FastAPI already provides. Either way, no new transport stack — it rides the control plane.
  • Web: no new deps — plain fetch client + existing React 19 stack.
  • Rust TUI: serde_json already available via existing store; no new crates expected.

Risks & mitigations

  • Rename breaks a hidden reader. Mitigated by compatibility views + one-release aliases + grep regression test.
  • Key leakage via snapshots/logs. Mitigated by the "masked() is the only emit path" rule and a security regression pin.
  • A2A spec evolution. v1.0 is stable but the ecosystem moves fast (signed Agent Cards, extensions); pin protocolVersion in the Agent Card and keep the bridge thin so bumps are localized to a2a/.
  • Exposing an agent endpoint widens the attack surface. The A2A RPC endpoint reuses the control-plane bearer token and binds to 127.0.0.1 by default; only the Agent Card is unauthenticated. Document explicitly that exposing it beyond localhost requires a reverse proxy with real auth.

Future work (out of scope)

  • OAuth/device-code subscription auth (Claude, OpenAI subscriptions) as an auth_mode.
  • OS keychain credential backend.
  • A2A client-side mode (Forge delegating sub-tasks to other A2A agents), input-required clarification round-trips, signed Agent Cards, and push-notification webhooks for task completion.
  • Editor integration via Agent Client Protocol (Zed-style stdio ACP) — a separate, smaller adapter if editor embedding is ever wanted; deliberately not conflated with this A2A work.

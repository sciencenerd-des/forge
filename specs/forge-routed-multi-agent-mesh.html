Purpose

Convert Forge's PGE graph from a fixed pipeline with guard conditions into a genuinely routed multi-agent mesh, where every LangGraph node is a declared agent with its own capabilities, tool allowlist, model profile and budget — and a first-class Router agent decides which agent runs next, records why, and streams that decision live to the Rust TUI and the React web console so an operator can watch, audit and override the routing in flight.

The end state: planner → auditor → executor → evaluator → planner stops being the topology and becomes just one possible path through a roster of specialists that the router selects between on evidence.

Problem

Forge already calls itself a multi-agent system, but the code does not implement one. Five specific gaps, each verified in the tree at a06d3cc:

1. The routers are guards, not routers

engine/src/graph.py compiles a static topology. Of its four nodes, two edges are unconditional (auditor → executor, executor → evaluator). The two "routers" only answer safety questions — planner_router asks "does a contract exist yet?" and "are we past the turn ceiling?"; evaluator_router asks "is the goal verified / blocked / out of turns?". Neither ever chooses which agent is best suited to the work, because there is never more than one candidate. The topology is a cycle with a bypass.

today what "routing" implies ───── ────────────────────── planner ──┬─► auditor ──► executor planner auditor coder tester │ │ ╲ │ │ ╱ └────────────────► │ ╲ │ │ ╱ ▼ ╲ ▼ ▼ ╱ evaluator ──► planner ► R O U T E R ◄ ╱ │ │ ╲ one path, guarded researcher │ reviewer evaluator chosen on evidence, per turn

2. A node is a procedure, not an agent

Nodes are plain functions over one shared AgentState TypedDict (engine/src/state/schema.py, 65 lines). There is no agent identity, no declared capability, no per-agent tool subset, and no per-agent budget. default_registry() in forge_runtime/tools.py hands the same eight tools to whoever asks — so the 955-line executor_node.py is simultaneously the coder, the build runner, the web researcher and the notebook editor. There is nothing to route between.

The one real foundation that does exist: forge_config.ROLES already routes a distinct model per role (planner/executor/auditor/evaluator/steward/general), and forge_runtime.llm.client_for(role) resolves it lazily. Agent identity is half-built already.

3. A working router exists and is dead code

SteeringEngine.choose_next() in forge_runtime/steering.py:66 is a complete, deterministic, dependency-aware policy returning execute | activate | decompose | repair_plan | verify_goal | blocked. It is exported from forge_runtime/__init__.py and never called anywhere in the repository (only its Lesson dataclass is used, by lessons.py and lesson_store_db.py). A tested routing brain is sitting on the shelf while graph.py re-implements a weaker version inline.

4. The GUIs cannot show routing, because routing emits nothing

run_pge.py:370 calls pge_graph.invoke(...) — a blocking call that yields nothing until the whole batch finishes. With no event to consume, control_plane/runtime_snapshot.py:186 reconstructs the current node by grepping the log tail for the four node names: 

def _current_node(lines: list[str]) -> str:
    text = " ".join(lines).lower()
    for node in ("evaluator", "executor", "auditor", "planner"):
        if node in text:
            return node

That single scraped string is the entire routing signal reaching both front ends: current_node: String in forge-api/src/types.rs:27,65 feeds the 2839-line Rust TUI, and web/src/App.tsx:77 polls it on a 1.5s timer. No agent identity, no reason, no alternatives, no history.

5. The operator cannot intervene at a decision point

forge_approvals and /approvals exist for actions (migrations/001_control_plane.sql), but the graph never calls LangGraph's interrupt(). An operator watching a run make a bad routing choice can only stop the run — never redirect it.

Solution

Eight ordered phases. Each is independently shippable and independently testable, and the first two are strictly behaviour-preserving so the regression suite in tests/regression/ stays the safety net throughout.

The four load-bearing decisions

A. Agents are declared, not implied

A new AgentSpec registry makes each node a declared agent: stable id, typed capabilities, a tool allowlist, a model role, a budget (turns / tokens / wall-clock), and explicit input/output contracts. Routing is only meaningful if candidates are distinguishable — this is what makes them distinguishable. It is also a real security tightening: the researcher stops holding write_file, the coder stops holding browser_fetch.

B. The Router is deterministic-first, model-second

Forge's whole thesis is reliability over cleverness for small models (ARCHITECTURE.md). A router that asks a 12B model "who should go next?" every turn would be exactly the fragility the project spent weeks removing. So:

  1. Policy tier — generalise the dead SteeringEngine into RoutingPolicy. Dependency-ready work, attempt ceilings, stagnation signatures, contract presence and failing-test classes are all decidable without a model. Expect this tier to resolve the large majority of turns.
  2. Model tier — invoked only when the policy returns AMBIGUOUS with two or more viable candidates. The model picks from a short enum with the candidate rationales in front of it — a task small models do reliably.
  3. Operator tier — an interrupt() when risk is high or manual routing is armed from the TUI/GUI.

Every decision records which tier produced it. That mechanism field is what later lets the eval suite prove the router is not just an expensive coin flip.

C. Handoff via Command, cooperation via the blackboard

LangGraph 1.2.7 is already installed (verified: Command, Send and interrupt all import cleanly) while graph.py is written in the pre-0.2 string-returning style. Agents will return Command(goto=..., update=...), which removes the hardcoded edge maps and lets the roster grow without editing the topology.

Agents must not cooperate by growing AgentState — that is how you get a 1 MB dict flowing through a 12B context. They cooperate through the durable blackboard that already exists: forge_memory_items, forge_file_changes, forge_test_runs, retrieved per-agent through forge_runtime/context_pack.py. State stays thin; artefacts stay durable and queryable.

D. Routing decisions are durable events, and the event is the product

forge_run_events already has everything needed — run_id, monotonic sequence with a uniqueness constraint, event_type, actor, and a jsonb payload. actor becomes the agent id. Swapping invoke() for stream(stream_mode="updates") turns the graph into an event source, the log-tail grep is deleted, and both front ends finally have something real to render.

The single biggest risk, stated up front. Genuine routing can reintroduce exactly the runaway failures Forge already fixed — docs/LESSONS.md and the comments in graph.py record a planner→planner KeyError crash, an executor↔evaluator ping-pong that produced 5000+ no-progress checkpoints, and a two-day hang on a poisoned contract. A free-form router is a superset of those failure modes. Phase 2 therefore ships the Routing Governor in the same phase as the router itself, never after: hop budget, oscillation detection, per-agent attempt ceilings, and a no-progress trip that falls back to the current fixed cycle.

[] Phase 1: Agent Contract & Registry

Give every node an identity without changing what any node does. At the end of this phase the graph behaves byte-identically to today — the only difference is that each node is now a declared agent with a capability set, a scoped tool allowlist, a model role and a budget. This is the vocabulary every later phase depends on.

  • [] Create engine/src/agents/__init__.py with a frozen AgentSpec dataclass: id, display_name, capabilities: frozenset[Capability], tools: tuple[str, ...], model_role: str, budget: AgentBudget, emits: frozenset[ArtifactKind], consumes: frozenset[ArtifactKind].

[] Phase 2: The Routing Kernel + Governor

Introduce the Router agent and the safety governor together. The roster is still the four original agents, so the router provably reproduces today's path — which is exactly the point: it proves the kernel is correct before there is anything interesting to route to.

1. Model the decision

  • [] Create engine/src/routing/decision.py with a frozen RoutingDecision: run_id, turn, from_agent, to_agent, mechanism (policy|model|operator|fallback), reason, confidence, candidates (each with its own score and rationale), state_digest.
  • [] Write migrations/005_routing_decisions.sql creating forge_routing_decisions with a FK to forge_runs(id) ON DELETE CASCADE, UNIQUE(run_id, turn, sequence), a jsonb candidates column, and an index on (run_id, turn). Follow the BEGIN;/COMMIT; + IF NOT EXISTS style of migrations 001–004.
  • [] Add the ORM model to control_plane/models.py and the response schema to control_plane/schemas.py.

2. Build the deterministic policy tier

  • [] Create engine/src/routing/policy.py. Wrap SteeringEngine.choose_next() and map its SteeringDecision.action onto agent ids: execute→coder, decompose→planner, repair_plan→planner, verify_goal→evaluator, blocked→END.
  • [] Fold in the guards currently inline in graph.py: contract-absent and contract-poisoned both route to auditor (preserve the _contract_poisoned check verbatim — graph.py records it as the fix for a two-day hang).
  • [] Return a three-state result: DECIDED(agent, reason), AMBIGUOUS(candidates), or TERMINAL(reason). Only AMBIGUOUS may reach the model tier.
  • [] Keep the policy pure — state in, decision out, no DB writes and no I/O — so it is exhaustively table-testable.

3. Build the Routing Governor

  • [] Create engine/src/routing/governor.py enforcing, in order: global hop budget per batch (PGE_MAX_HOPS, default 3 × PGE_MAX_TURNS); per-agent consecutive-turn ceiling from AgentBudget; oscillation detection over the last N transitions (A→B→A→B and 3-cycles) reusing the existing recent_action_signatures discipline.
  • [] On any trip, emit a routing.governor_tripped event and fall back to the fixed cycle for the remainder of the batch, recording mechanism="fallback". Degrading to today's known-good behaviour is always available and always visible.
  • [] Preserve the durable task limits from evaluator_with_control (MAX_ATTEMPTS_PER_TASK, MAX_NO_PROGRESS_ATTEMPTS) — move them into the governor rather than duplicating them.
  • [] Guarantee the governor can never route to a non-existent node: validate to_agent against AgentRegistry.ids() before returning. This is the direct fix for the KeyError: 'planner' class of crash documented in graph.py.

4. Build the Router agent

  • [] Create engine/src/routing/router_node.py: run policy → on AMBIGUOUS run the model tier with a strict JSON schema over the candidate enum (mirror the *_SCHEMA style in forge_runtime/llm.py) → pass the result through the governor → return Command(goto=agent_id, update={...}).
  • [] On model-tier failure (timeout, unparseable JSON, out-of-enum agent), fall back to the policy's highest-scoring candidate and record mechanism="fallback". A router must never be able to take the run down.
  • [] Persist every RoutingDecision before the Command is returned, so a crash mid-handoff leaves an auditable trail.

5. Rewire the graph as a hub

  • [] Rewrite engine/src/graph.py: set_entry_point("router"); register all agents; delete planner_router and evaluator_router; have each agent return Command(goto="router") by default.
  • [] Preserve the once-per-cycle checkpoint discipline — _checkpoint()'s comment records that per-node checkpointing ballooned the table to 10k+ rows. Checkpoint after the evaluator, not after every hop.
  • [] Add PGE_ROUTING_MODE = fixed|policy|hybrid (default hybrid), where fixed reproduces the pre-plan topology exactly. This is the rollback switch and the A/B lever for Phase 8.

6. Testing Strategy

Table-driven pytest over the pure policy; adversarial state fixtures for the governor; and the existing regression suite run under PGE_ROUTING_MODE=fixed and hybrid to prove equivalence on the old path. Edge cases: oscillation, hop exhaustion, model returning an unknown agent id, model timeout, terminal-with-blockers, and an empty roster.

[] Phase 5: The Routing Event Spine

Replace the blocking invoke() and the log-tail grep with a real streamed event feed. Everything the TUI and the web console will render is defined here — this phase is the contract both front ends consume, so it lands before either of them.

1. Define the event contract

  • [] Create forge_runtime/agent_events.py emitting to forge_run_events with actor = agent_id: agent.started, agent.finished, agent.tool_called, agent.tool_denied, routing.decided, agent.handoff, routing.governor_tripped, routing.interrupt_requested, budget.exceeded.
  • [] Reuse the table's existing UNIQUE(run_id, sequence) for monotonic ordering — resumable cursors come free, and both front ends can reconnect with ?after=.
  • [] Publish the payload schemas in contracts/ alongside the existing control-plane schemas, and pin them with a fixture test so a payload change cannot silently break the Rust client.

2. Stream the graph

  • [] Replace pge_graph.invoke(...) at run_pge.py:370 with pge_graph.stream(..., stream_mode="updates"), emitting an event per node update while preserving the existing final-state handling and the batch/stagnation accounting around it.

Questionables

Open decisions where a different answer changes the work. Each records the assumption this plan proceeds under, so a reader can override it deliberately rather than discover it late.

Does genuine routing actually beat the fixed cycle for small local models?

Unknown, and deliberately not assumed. The fixed cycle is heavily tuned scar tissue; a router adds a decision point that can be wrong. Specialisation should help most where the current executor is over-scoped (an unknown API sending it down a guess-and-check spiral), and hurt where routing overhead dominates a short goal. This is precisely why Phase 8 defines its promotion criterion before running, why PGE_ROUTING_MODE exists, and why a negative result is an acceptable, publishable outcome. Phases 5–7 deliver value regardless of the verdict.

Hub-and-spoke, or a full mesh where any agent can hand off to any other?

This plan assumes hub-and-spoke with declared peer exceptions. A full mesh makes every agent a router, which multiplies the surfaces that can oscillate and destroys the single auditable decision point the GUIs depend on. Declared peer handoffs (coder → tester) recover most of the latency benefit while keeping the governor and the event stream authoritative. Revisit only if the trace shows the hub is a measurable bottleneck.

Should the router use a model at all?

Assumption: yes, but rarely and never load-bearing. A pure-policy router is more predictable and cheaper, and it may well be sufficient — the tier-mix metric in Phase 8 will show how often ambiguity actually arises. If the model tier fires on under ~5% of turns and does not beat the policy's top candidate on those, delete it. The architecture is deliberately built so that deleting the model tier is a one-line change, not a redesign.

Is splitting the executor worth destabilising 955 lines of hardened code?

This is the highest-risk phase. executor_node.py encodes real scar tissue — argv-vs-shell handling, venv PATH resolution, placeholder detection, sandbox interaction. The mitigation is strict: lift shared machinery unchanged into _execution.py first, verify green, and only then split responsibilities. If the split proves destabilising, a viable fallback is a single executor agent with capability-scoped modes — the router still chooses a mode and the trace still explains it, but there is one code path. That retains most of the routing value at a fraction of the risk.

Where do parallel agents write?

Assumption: only one writer per workspace, ever. The sandbox in forge_runtime/sandbox.py is a per-project container with a Docker-managed volume; concurrent writers into one workspace is a corruption bug. Phase 4 therefore forbids scheduling two write_file holders together. Genuine parallel editing would need per-agent workspace branches and a merge step — a substantially larger design, explicitly out of scope here.

Does the stream ticket weaken control-plane auth?

It is a real widening of the auth surface and is treated as such. Mitigations: TTL ≤ 60s, single-use, bound to one run_id, never logged, and issued only to an already bearer-authenticated caller. The alternative — keeping the browser on polling forever — is what the code comment at api.py:262 settles for today. If even a scoped ticket is unacceptable, the fallback is a same-origin proxy that injects the header, which the Vite dev proxy already models.

Is AgentState still the right carrier?

Assumption: yes, kept deliberately thin. State carries routing control fields only; artefacts go to the durable blackboard. The temptation as the roster grows will be to add one more field per agent — that path ends in a state dict too large for a 12B context. If state grows past a stated budget, that is the signal to move the field to the blackboard, not to raise the budget.

No new runtime dependencies are required. Rejected approaches

  • Adopt a multi-agent framework (CrewAI, AutoGen, swarm libraries). Forge's value is in what it does around the loop — durable Postgres state, the sandbox boundary, the independent evaluator, the acceptance gate. A framework would own the loop and force all of that to be re-earned through its extension points. LangGraph is already the substrate and already supports everything needed.
  • Pure-LLM supervisor routing. Rejected as the primary tier for the reason stated throughout: a model deciding topology every turn is exactly the fragility Forge removed. It survives as the ambiguity tiebreak only.
  • Agents as separate processes / A2A peers. Forge already has an A2A adapter (forge_a2a/, docs/A2A.md), so cross-process agents are reachable later. But in-process nodes share the sandbox, the DB session and the checkpoint — going cross-process first would buy isolation nobody asked for at the cost of the durability story. Revisit if agents ever need to run on different machines.
  • Fat AgentState as the cooperation medium. Simplest to write, fatal at roster scale for small-model contexts. The durable blackboard already exists and is queryable.

Sequencing rationale

The order is chosen so that value lands early and risk lands late. Phases 1–2 are behaviour-preserving and reversible via PGE_ROUTING_MODE. Phase 5 (the event spine) deliberately precedes both GUIs, because a front end built against a scraped string would have to be rewritten. Phase 3 — the executor split — is the highest-risk change and is placed after the kernel is proven but before the GUIs, so the front ends are built against the final roster. Phase 8 decides the default and is allowed to conclude "keep it off".

Research grounding

AI_DOCS/research/INDEX.md sets a strict convention: each entry states what the paper establishes and what Forge does with it, and there is an explicit "cited but not verifiable" section. The following should be fetched and indexed the same way before Phase 2 hardens the router design. Listed as directions to verify, not as settled citations:

  • CoALA (Sumers et al., 2023) — already in the library. Its decision-procedure framing (propose → evaluate → select over an action space) is the closest published analogue to the three-tier router, and its memory taxonomy already governs Forge's memory_type naming. This is the most directly applicable existing entry.
  • Reflexion (Shinn et al., NeurIPS 2023) — already in the library. Relevant to the reviewer agent: verbal self-reflection on failure, re-injected, beats blind retry.
  • AutoGen (Wu et al., 2023) — multi-agent conversation framework whose group-chat manager is a routing analogue. Worth reading specifically for how it handles speaker selection and termination, which are the same two problems the governor solves.
  • Role-specialised software-agent systems (the MetaGPT and ChatDev line, 2023) — prior art for splitting a coding agent into declared roles. Verify the specific claims before citing; the useful question is whether their reported gains survive at 12B scale, which is Forge's regime.
  • LLM query routing (the RouteLLM line, 2024) — routing between cheap and strong models by predicted difficulty. Directly applicable to Forge's per-role provider profiles: the same signals that pick an agent could pick a model tier for that agent.

Follow the INDEX.md discipline: if a paper cannot be located or its claims cannot be verified, record it under "cited but not verifiable" and treat it as directional. Do not let an unverified citation justify a design decision.

Future work, explicitly out of scope

  • Cross-process / cross-machine agents over the existing A2A adapter.
  • Per-agent workspace branches with a merge step, enabling true parallel editing.
  • Learned routing — using forge_routing_decisions plus outcomes as training signal to improve the policy tier. The schema is designed to make this possible later; nothing in this plan depends on it.
  • Per-agent model auto-selection by predicted difficulty (the RouteLLM direction above).

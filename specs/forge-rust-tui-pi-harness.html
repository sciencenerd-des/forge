Purpose

Turn experimental/forge-cli from a disconnected skeleton into the primary operator entry point for Forge: a single fast Rust binary with a minimalist, Pi-inspired TUI that (1) fully drives the Python PGE harness through the control plane (runs, live events, approvals, providers), and (2) hosts interactive coding-agent sessions by using the Pi coding agent as the session harness over its documented RPC protocol. The scope is deliberately bounded to the operator path plus the Pi seam; a native Rust tool layer and a no-Node native agent loop are recorded as evidence-driven follow-up proposals (see Backlog), not phases of this plan.

Problem

The Rust CLI today is ~1,200 lines that never touch the real system: it keeps its own local JSON store of projects/goals/runs that nothing else reads, its TUI is a read-only two-pane viewer polling $FORGE_HOME/logs/pge_runs/runs.json every 250 ms, and it has no HTTP client, no SSE, no approvals, no interactive agent. Meanwhile every real capability lives behind the FastAPI control plane on :8787 (bearer-token REST + SSE: /runtime/runs/start, /runtime/runs/{project}/stop, /runs/{id}/events/stream, /approvals, /providers, A2A JSON-RPC) — reachable only through the React web console or raw curl. There is no fast, keyboard-first terminal surface, and no way to hold an interactive coding-agent conversation from the terminal at all. Separately, the user's target UX — the Pi coding agent — is a TypeScript program; the design question is which parts of pi to reuse as a harness and which parts must be custom Rust.

Solution

Grow the workspace to exactly three crates — forge-cli (binary + TUI), forge-api (control-plane client), forge-pi (Pi RPC bridge) — and split responsibilities along a harness decision matrix (full table in Notes): pi is the harness for interactive coding-agent sessions — spawned as a child process in pi --mode rpc (strict LF-delimited JSONL over stdin/stdout), giving us its agent loop, its built-in tool set (read/write/edit/bash/grep/find/ls), 8+ providers with OAuth, streaming, session branching/compaction, and cost tracking for free; everything Forge-specific is custom Rust — the control-plane client (REST + SSE) and the operator TUI (ratatui, pi's minimalist design language). Work is ordered so the seams are proven first (Phase 0 contract-and-spike), the operator path ships first (Phases 1–2, no Node required), and the Pi session lands on top (Phase 3). The TUI has exactly two top-level modes — Operator (runs, events, approvals, providers) and Session (agent transcript + editor) — switched with tab, honoring pi's "minimal core, no spaceship" philosophy.

[] Phase 2: Operator TUI (second shippable milestone)

Replace the read-only viewer with a live, keyboard-first operator surface in pi's design language. Ships independently of pi/Node.

1. App shell & event architecture (input can never starve)

  • [] Two queues, not one: a high-priority channel for input/control events (keyboard, resize, shutdown) and a separate bounded bulk channel for SSE/stream events. The draw loop always drains priority first.
  • [] Bulk events are batched and coalesced: SSE lines append to a capped model buffer (10k-line scrollback) and set a dirty flag; redraw notifications coalesce so a burst produces one frame, not N. No per-line traffic through the UI channel.
  • [] tui/theme.rs: amber/verdigris palette matching this spec; all colors via the theme. Global keys: ? help, q quit, tab mode switch, j/k select, enter open — nothing else at top level.

2. Operator views

  • [] Runs pane: live RuntimeRunSnapshot list; when offline, the OfflineRunManifest view renders with an unmissable OFFLINE banner — live and offline states are visually distinct, never merged.
  • [] Detail pane: selected run's RunEvent stream via events_stream (follow mode), log-tail fallback from the manifest's log path.
  • [] Actions: s start run (inline goal editor → RunStartResult), x stop selected project (confirm; project-addressed per the API), p providers panel (list/test/set).
  • [] Approvals: a view + inline bar the moment a pending approval exists; y/n with required reason → decide. The human gate for PGE external actions — the most important widget in the app.

3. Testing Strategy

Deterministic UI tests with ratatui's TestBackend (buffer snapshots per view/state, replayed fixture events). Edge cases: zero runs, offline mode, 80×24 resize, and the flood case below. The flood test asserts maximum input latency, not merely "no drops": under 1,000 bulk events/s for 30 s, a synthetic keypress must reach the app state in < 50 ms (p99).

  • [] cargo test -p forge-cli — TestBackend snapshots for runs/detail/approvals/offline/help states pass.
  • [] cargo test -p forge-cli --test flood -- --nocapture — input p99 latency < 50 ms under 1k events/s; memory stable; scrollback cap enforced.
  • [] cargo run -p forge-cli -- tui — manual smoke: start a run, watch live events, decide an approval, kill the control plane and watch the OFFLINE banner appear.

[] Phase 3: Pi Session Mode

Promote the Phase 0 spike into forge-pi and render the pi experience in the TUI. Pi supplies the loop and its built-in tools; the Rust side is protocol + rendering only.

1. forge-pi protocol client

  • [] process.rs: spawn pi --mode rpc with configurable flags (--provider/--model/--session/--no-session/--session-dir); kill-on-drop; stderr → tracing log; absence detection with install hint (npm i -g @earendil-works/pi-coding-agent); warn on version ≠ pinned.
  • [] codec.rs: strict JSONL framing — split on \n only, strip trailing \r, never Unicode-aware splitting; compact serialization with monotonic ids.
  • [] protocol.rs: typed commands (prompt, steer, follow_up, abort, new_session, get_state, set_model, cycle_model, get_available_models, set_thinking_level, compact, switch_session, fork, get_session_stats, get_commands) and events with #[serde(other)] catch-alls — unknown-event tolerance is resilience, not a compatibility claim; the pinned version + fixtures are the compatibility claim.
  • [] PiClient: id-correlated oneshot responses; broadcast event stream; extension_ui_request (select/confirm/input/editor + notify/setStatus/setWidget/setTitle) exposed as a DialogRequest stream with timeout auto-resolve; graceful shutdown (abort → EOF → wait → kill).
  • [] Define one internal SessionEngine trait in forge-cli with only the Pi implementation — the seam exists for a future backend, but no second implementation is built to justify it.

2. Session UI

  • [] Transcript widget: streamed deltas (text_delta, dimmed thinking_delta, toolcall_* as compact expandable tool chips); incremental append into the capped buffer via the Phase 2 bulk queue — never re-layout history on a delta.
  • [] Editor (tui-textarea): enter send, alt+enter newline, esc during streaming → abort/steer/follow-up bar. Footer: model, thinking level, context %, session cost from get_session_stats.
  • [] ctrl+m model picker (get_available_models); ctrl+t thinking level; ctrl+k compact (tokens before/after); ctrl+r session picker (resume via switch_session, branch via fork); forge session --resume/--fork/--no-session map to pi flags.
  • [] Extension-UI dialogs render as centered modal overlays; notify/setStatus/setWidget map to footer widgets — pi extensions work unmodified.
  • [] Promote to goal with a review gate: ctrl+g opens a confirmation editor pre-filled with goal title, description/context, target project, and a warning if that project already has an active run. Only explicit confirm calls POST /runtime/runs/start. Nothing fires implicitly from "last user intent".

Notes

The harness decision matrix (the core research answer)

Pi (earendil-works/pi, formerly badlogic/pi-mono, MIT, TypeScript, by Mario Zechner) is a minimal coding agent: built-in tools read/write/edit/bash/grep/find/ls, a <1,000-token system prompt, no plan mode / sub-agents / MCP in core, with everything else pushed to extensions. Critically for us, it exposes a documented RPC mode (--mode rpc): strict LF-delimited JSONL over stdin/stdout with id-correlated commands, a rich streamed event model, and an extension-UI sub-protocol — explicitly designed for non-Node clients. That is the reuse seam.

Control-plane contract — the shapes are NOT interchangeable

  • /runtime/runs returns a synthesized snapshot (runtime_snapshot.py) keyed by id — model it as RuntimeRunSnapshot.
  • /runs/{id} returns a durable DB record — model it as DurableRun.
  • Stop is project-addressed (/runtime/runs/{project_id}/stop); event streaming is run-addressed (/runs/{run_id}/events/stream). The type system must prevent passing one id where the other belongs (newtype ids: ProjectId, RunId).
  • The detached launcher manifest (pge_launcher.py) is a third shape (OfflineRunManifest), mirrored separately into durable event tables — it is a fallback view, never merged with live data.
  • Token file: Python repairs loose permissions (chmod 0600) and continues (forge_runtime/auth.py); Rust mirrors that repair-and-continue behavior.

Pi RPC protocol — implementation crib

  • Framing: split stdout on \n only; strip trailing \r; never use Unicode-aware line splitting (JSON payloads may contain U+2028/U+2029).
  • Correlation: commands carry optional id; responses echo it with type:"response", success, optional error. Events carry no id and interleave freely.
  • Key commands: prompt (base64 image blocks, streamingBehavior: steer|followUp), steer, follow_up, abort, get_state, set_model {provider, modelId}, set_thinking_level off…max, compact, session ops (switch_session, fork, get_entries {since}, get_tree, get_session_stats).
  • Event spine for the transcript: agent_start → turn_start → message_start → message_update(text_delta|thinking_delta|toolcall_delta)* → tool_execution_start/update/end → message_end → turn_end → agent_end → agent_settled.
  • Extension UI: extension_ui_request {id, method} where method ∈ select/confirm/input/editor (dialog — must respond) or notify/setStatus/setWidget/setTitle (fire-and-forget). Respond with extension_ui_response matching id.
  • No version handshake exists. Compatibility = the pinned version (installed and tested in CI) + recorded fixtures. Unknown-event tolerance via serde catch-alls is resilience only, not a compatibility claim.
  • Package: npm i -g @earendil-works/pi-coding-agent; repo earendil-works/pi (the old badlogic/pi-mono redirects).

Backlog — deferred, evidence-driven follow-ups (not part of this plan)

  • forge-tools native tool layer: pi already ships read/write/edit/bash/grep/find/ls. Before building replacements: benchmark pi's tools on real end-to-end agent latency in this repo. If (and only if) tool execution is a measured bottleneck, the correct integration is a small TypeScript pi extension that calls pi.registerTool() and schema-validates arguments before shelling into a Rust forge-tools binary. A README alone does not register tools. Secondary consumer worth more: a Rust tool backend for the PGE executor (replacing forge_runtime/tools.py hot paths), which needs no pi integration at all — likely the better first RFC.
  • forge-agent no-Node native loop: separate RFC. It would recreate streaming, tool calling, session persistence, and abort semantics that choosing pi avoids. Prerequisites: demonstrated demand for Node-free sessions, and the SessionEngine trait from Phase 3 as the adapter seam (which exists but has only the Pi implementation until then).
  • A2A client + forge a2a send: small post-MVP addition to forge-api.

Rejected alternatives

  • Port pi-tui to Rust wholesale — ratatui already implements differential rendering; we copy the aesthetic, not the framework.
  • Embed forge logic as pi TypeScript extensions (pi as the outer shell) — inverts ownership: the operator surface would then require Node even for pure monitoring. Rust shell + pi subprocess keeps the no-Node operator path intact.
  • Zed's Agent Client Protocol (ACP) as the session seam — pi doesn't speak ACP; pi's RPC is simpler and matches the chosen harness. Revisit only if a second agent backend is added (the SessionEngine trait is the adapter point).
  • Rewrite the PGE engine in Rust — PGE latency is dominated by LLM inference and test execution, not interpreter overhead. The Rust wins that matter are in the interactive path.
  • Hand-written axum mock as the contract oracle — a mock that "mirrors" FastAPI duplicates the contract; if mock and client share a wrong assumption, tests stay green. Replaced by Python-generated fixtures + OpenAPI export; axum retained only for transport behavior.
  • MCP for tool integration — pi deliberately omits MCP; its extension model covers the need.

Risks & mitigations

  • Pi protocol drift (no version handshake): pin the exact version in CI; recorded fixtures are the contract; serde catch-alls for resilience; the fake-pi binary doubles as the contract spec.
  • Node dependency creep: hard rule — Operator mode must never require pi/Node; CI's main job runs the full suite without pi installed.
  • Control-plane contract drift: Python fixture-export tests + Rust fixture-decoding tests run in the same CI pipeline; a contract change fails loudly on both sides.
  • TUI input starvation under event floods: dual queues (priority input / bulk stream), coalesced redraws, capped model buffer; the flood test asserts p99 input latency < 50 ms, not merely "no drops".
  • Implicit durable actions: promote-to-goal always passes through a confirmation editor showing title, description, project, and active-run status before any POST.
